OpenClaw

OpenClaw is Shane's primary AI surface. It is the multi-agent gateway that sits between him, the underlying model providers (OpenAI Codex, OpenRouter, Anthropic, Google), and every channel he uses to reach an agent — Telegram from the phone, the local terminal at the desk, the ACP and MCP protocols for tool integrations. There is a separate OpenClaw AI Gateway topic that describes the gateway as a concept; this page treats OpenClaw as an entity with its own personality, its own daily behaviour, and its own role in Shane's life.

The distinction matters. From inside the system, OpenClaw is a config file at ~/.openclaw/openclaw.json, a workspace directory at ~/.openclaw/workspace/, a cron schedule at ~/.openclaw/cron/jobs.json, and a collection of skills at ~/.openclaw/skills/. From the outside, it is the thing Shane talks to when he wants to talk to an agent. That second framing is what this page is about.

What it is

OpenClaw is a self-hosted multi-agent gateway that runs locally on macOS, exposes a unified routing layer over multiple model providers, and connects to the outside world through Telegram, Discord (currently disabled), the Agent Communication Protocol (ACP), and the Model Context Protocol (MCP). It binds to a loopback gateway port (18789) for control, registers skills against the open Agent Skills standard, and uses kernel-enforced sandboxing via nono to keep agent file and network access bounded.

Concretely, the live config exposes:

  • Multiple model providers wired through auth.profiles: an OpenAI Codex profile (used for the primary gpt-5.4 and gpt-5.3-codex models that power most agent runs) and an OpenRouter profile (used for fallbacks, alternate model families, and specialty models).
  • A model alias map that lets agents reference models by short names — gpt5, mini, sonnet, flash, haiku, codex, codex53, codex-mini, gpt54, qcoder, devstral, codestral, deepseek-code — instead of full provider/model strings. The default primary is openai-codex/gpt-5.4 with fallbacks to openai-codex/gpt-5.3-codex and openrouter/google/gemini-3-flash-preview.
  • The Telegram channel enabled, Discord disabled. Telegram is the one out-of-band control channel that actually carries production traffic.
  • A subagent budget of 2 concurrent and 2 spawn-depth max, governed by the same model defaults as the parent.

The agent zoo

OpenClaw runs four named agents in the live agents.list config:

  1. Best Robot (Main Agent) — the default conversational agent. Inherits the global model defaults, talks to Shane through Telegram and the local terminal, and is the surface that the morning briefing and most ad-hoc requests land in.
  2. Coder Agent — specialised for code work. Pinned to openai-codex/gpt-5.4 primary with gpt-5.3-codex and gpt-5.1-codex-mini fallbacks. This is what gets invoked when a session is long-form engineering rather than conversational.
  3. Trader GPT5 Agent — the dedicated trading-research agent on the gpt-5.4 family. Lives on its own model line so its prompts and risk posture stay isolated from the main agent's general-purpose context.
  4. Trader GPT54 Agent — a parallel trading agent on the same primary model with the same fallback chain. Two trader agents exist because trading workflows benefit from running independent reasoning paths against the same evidence and comparing the outputs.

Each agent has its own session scope and its own personality grounding (see below). They are not interchangeable; routing a coder request to the main agent or a trading question to the coder agent costs context and quality.

The personality stack

OpenClaw grounds every fresh agent run in three workspace files that live at ~/.openclaw/workspace/:

  • SOUL.md — the underlying values and tone the agent should carry. The longest of the three (~480 words). This is what makes Best Robot read as Best Robot rather than a generic Claude or GPT. See Agent Personality Design for the design discipline behind it.
  • IDENTITY.md — who the agent is, what it is allowed to claim about itself, what register it operates in. (~226 words.)
  • USER.md — who Shane is, what he is working on, what his preferences are. (~304 words.) This is the file that makes the agent useful on the first message of a fresh session instead of needing five rounds of warm-up.

The three files together are about a thousand words of grounding that load before every meaningful agent interaction. They are also why a wiped session feels continuous — the next agent does not know the previous conversation, but it knows the same Shane, the same values, and the same operating context.

Adjacent files in the same workspace — HEARTBEAT.md, SHIELD.md, MEMORY.md, TOOLS.md, AGENTS.md, README.md — extend the grounding for specific runtime modes (heartbeats, safety posture, persistent memory, tool usage, multi-agent coordination).

The cron-driven scheduled tasks

OpenClaw's cron layer at ~/.openclaw/cron/jobs.json is what turns the gateway from "an agent you can talk to" into a daily operating system. The currently-enabled jobs (as of 2026-05-03) include:

  • Morning Briefing — daily 7:00 AM Pacific
  • Weekly PinchBench + Stack Review — Monday 8:45 AM
  • Bitcoin + El Salvador Pulse — Mon/Wed/Fri 8:30 AM
  • ElSalKB Daily Randomized Refresh — daily 4:20 AM
  • Weekly Meme Delivery — Saturday 10:23 AM
  • Shanepedia One Bet — Tue/Thu/Sat 2:37 PM
  • Weekly Reset Brief — Sunday 8:00 PM
  • OpenCluck Weekly Hardware Spark — Wednesday 10:00 AM
  • Shanepedia Random Spark — daily 12:30 PM
  • Shanepedia Daily Page — daily 11:00 AM

A handful of additional jobs are configured but disabled (the trip-window briefings, the OpenCluck daily lesson, several ElSalKB lane jobs). Disabled jobs stay in the file as documentation — the schedule contains the history of what has been tried.

The cron rhythm is detailed in Operating rituals; this page just notes that it exists and that it is the difference between OpenClaw as infrastructure and OpenClaw as a partner.

How Shane uses it daily

Most days, the interaction sequence is:

  1. 7:00 AM — the morning briefing lands in Telegram. Shane reads it on the phone before the desk session.
  2. Through the day — ad-hoc Telegram messages from the phone, terminal sessions at the desk, agent runs from skills (/wiki, /meme, etc.).
  3. Heartbeats every two hours — the main agent checks in if there is anything worth flagging.
  4. Asynchronous research — the cron-driven Shanepedia and ElSalKB jobs feed the wiki without requiring direct supervision.
  5. Sunday 8:00 PM — the weekly reset closes the loop and frames the following week.

The intentional design is that OpenClaw is always reachable but rarely demanding. The gateway initiates contact at known cadences (morning, heartbeats, Saturday meme, Sunday reset) and otherwise waits to be addressed. That asymmetry is what makes a 24/7 AI surface tolerable for years instead of months.

Why this matters

OpenClaw is the foundational entity that almost every other lane in Shanepedia routes through. The Codex Obsidian LLM wiki loop runs on its skills. The Operating rituals are scheduled in its cron. The Agent Personality Design is implemented in its workspace files. The Shane Neeley entity's daily operating mode is, in practice, a relationship with this system.

If OpenClaw goes down, the wiki still exists as plain markdown and the projects still exist as files, but the system that turns them into a daily operation stops. That is what makes it an entity worth treating as a first-class part of Shanepedia rather than a footnote in a tooling page.

Stance

The right way to think about OpenClaw is not as a chatbot, not as a productivity tool, and not as an AI wrapper. It is a primary AI surface — the place where Shane and an agent meet, on a schedule, with shared grounding, across multiple channels and devices. Almost no one outside specialised research labs runs anything like this in 2026, and that is the point: OpenClaw is the proof that a single founder can operate a real multi-agent system locally, with kernel-enforced sandboxing, with model fallbacks, with cron-driven rituals, and with a personality stack that makes the system feel continuous across sessions. The lesson worth carrying forward — and the lesson the Agentic business studio offer should be built on — is that the gateway is the product, not the model.
