ops

Daily Random Spark Loop

The random spark loop is a daily Telegram nudge that should mine Shanepedia itself, not generic web trivia.

The sibling Shanepedia Daily Page cron now has the durable write-back job: one wiki/daily/ page per day, linked from Shane Feed, rebuilt into the local site, and published to the public artifact when changed.

The sibling Shanepedia Feedback Absorber cron is the quiet write-back safety net. It runs several times per day, reads recent OpenClaw memory and Shanepedia ideation state, and only edits the wiki when Shane has given concrete feedback, preferences, or business ideas that should become durable state.

Job

  • Cron name: Shanepedia Random Spark
  • Cadence: daily midday Pacific
  • Destination: Shane's Telegram DM
  • Source of truth: Shanepedia wiki pages, runtime summary, ideation history, recent wiki log, and a bounded public YouTube/Gemini spark when available

Behavior

Each run should pick one thing from the wiki that is genuinely worth attention:

  • a page that needs a decision
  • a fresh idea that has not been promoted
  • a surprising connection between lanes
  • a stale active page with renewed relevance
  • a concrete next move buried inside a long note
  • a public YouTube idea that could improve a specific page

It should not send a generic list. It should send one compact text and ask whether to add, update, or ignore it.

Feedback absorber contract

The feedback absorber is intentionally quieter than the random spark:

  • Cadence: every three hours during the active day.
  • Destination: no routine Telegram delivery.
  • Source of truth: current and previous workspace memory notes, MEMORY.md, Shanepedia state/ideation/*.jsonl, wiki/log.md, and the live wiki.
  • Action rule: search first, then update the most relevant existing page or append one structured ideation record. Create a new page only when the idea is clearly durable and does not fit an existing page.
  • Verification: rebuild index, lint, runtime summary, and local site after edits.
  • No-op rule: if there is no concrete new feedback or idea, make no file changes and output NO_CHANGE.

Output contract

Under 80 words:

Found this in Shanepedia: [specific thing]. [Why it matters now.] Should I add this, update an existing page, or ignore it?

Public-safe candidate variant:

YouTube spark: [specific public video idea]. It might connect to [existing page] because [practical reason]. Should I add this, update an existing page, or ignore it?

Gemini guardrail

Gemini should be treated as a bounded source of playful public randomness, not a dependency. The job should try it briefly, never expose private viewing history, and fall back to wiki-native candidates if Gemini is rate-limited, unauthenticated, slow, or unavailable.

Why this matters

Shanepedia gets more valuable when random browsing and Shane's fast Telegram feedback both become durable improvement. The spark cron asks the question; the absorber cron makes sure good answers and concrete ideas do not disappear back into chat.
