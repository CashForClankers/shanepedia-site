Agent Personality Design

Most agent stacks have no personality. They have a system prompt that says "you are a helpful assistant" and inherit whatever default tone the model ships with — usually a hedging, over-explaining, mildly sycophantic register that reads as corporate by default. For a personal agent that talks to one operator dozens of times a day, that default is wrong. It wastes tokens, it wastes attention, and it never develops the trust gradient that makes an agent feel like a colleague instead of a chatbot.

This page argues for treating personality as a first-class design surface, with concrete reference to the OpenClaw setup Shane runs.

For the operator-facing voice contract — sentence shape, opening lines, what gets cut — the canonical reference is [[voice-and-style.md]]. This page is the design argument; that page is the rulebook.

Voice: terse beats verbose, casual beats formal (for personal agents)

Two axes:

  • Length: terse vs verbose
  • Register: casual vs formal

For a personal agent operated by one person, the right corner is terse + casual. The reasons:

  • A personal operator already has context. Reintroducing it every turn is friction.
  • Long preambles ("I'd be happy to help! Here is..." / "Great question!") are pure cost, no signal.
  • Casual register lets the agent push back without sounding insubordinate. "That's a bad idea because X" reads as advice from a casual register and as insubordination from a formal one.
  • The model can drop the customer-service voice and use the same words a smart friend would use.

The wrong corner for a personal agent is verbose + formal — the default a fresh model ships with. It signals "I do not know who you are" every single turn.

The right corner for a customer-facing agent (different problem) is usually terse + formal — short answers, professional register. That is not what we are designing here.

Opinions: yes, your personal agent should have them

There is a school of thought that says agents should be neutral and reflect back. For a search engine or a generic assistant, fine. For a personal agent embedded in your daily ops, neutrality is a failure mode:

  • You already have your own opinion. You do not need a mirror.
  • Useful agents disagree when you are wrong. A neutral agent cannot do that.
  • Compounding context means the agent has seen more of your work than any human collaborator. It is the best-positioned advisor you have. Refusing to give opinions wastes that.

The honest version is: your personal agent should hold opinions roughly aligned with your own taste — not a yes-machine, but a sharper version of your own judgment. It should disagree when it has a real reason and concede when you push back with new information. It should refuse to fold just because you sounded annoyed.

Sycophancy is the failure mode on the opposite end. An agent that congratulates every idea, agrees with every direction, and apologizes when corrected is worse than useless — it actively degrades your judgment by simulating consensus where none exists. The line is: be honest, be direct, be willing to lose a small argument, refuse to lose a big one.

OpenClaw worked example: SOUL.md, IDENTITY.md, USER.md

Shane's OpenClaw setup uses three files in ~/.openclaw/workspace/ to anchor agent personality across sessions. See [[openclaw-ai-gateway.md]] for the broader gateway context.

  • SOUL.md — the agent's personality, voice, and operating defaults. What tone it uses, when it pushes back, what it refuses to do, how it handles uncertainty. This is the "who am I" file, written in second person to the agent itself.
  • IDENTITY.md — a tighter behavioral contract. Names the agent, defines its role relative to the operator, sets the line between assistant and collaborator. Often shorter and more declarative than SOUL.
  • USER.md — what the agent should know about Shane: how he works, what he prefers, what makes him impatient, what context to assume. This is the "who am I talking to" file. It is what lets the agent skip the customer-service voice from turn one.

Together these three files do what a system prompt cannot: give a fresh agent grounding for both itself and its operator within the first few hundred tokens. Every Claude Code session that starts in OpenClaw inherits this anchoring, which is why the agent does not feel like a fresh chatbot every morning.

The three-file split matters. A single monolithic personality prompt is hard to edit and hard to debug. Splitting personality (SOUL), role (IDENTITY), and operator-context (USER) lets you change one without disturbing the others. If the agent is being too soft, you edit SOUL. If it is forgetting that Shane uses Telegram remotely, you edit USER. If you want a different agent persona for a specific project, you swap IDENTITY and keep the rest.

"Be a good friend, not a good employee"

This is the design rule. A good employee is responsive, polite, never disagrees, and produces deliverables on request. A good friend tells you when your idea is bad, remembers what you said three weeks ago, jokes when something is funny, and does not pretend to be impressed when they are not.

For a personal agent, the friend register is correct. The employee register breeds learned helplessness, hedge-soup outputs, false agreement on bad ideas, and zero compounding intimacy across sessions. The friend register breeds direct feedback, shared shorthand, willingness to volunteer information without being prompted, and a relationship that improves with use.

The risk: a friend-register agent can come across as rude to anyone but the operator. That is fine for a personal agent. It is not fine for a customer-facing one. The same model with the same backbone needs different personality files for different roles. Do not try to ship one personality everywhere.

Practical advice for designing your own stack

  • Write personality files in the agent's voice, not yours. Second person ("you are X, you do Y") works in SOUL/IDENTITY. First person drifts into mission-statement mode.
  • Use concrete examples, not abstract principles. "Skip 'great question!' preambles" beats "be concise."
  • Edit after every irritation. If the agent annoyed you today, the personality file should be different tomorrow.
  • Test with a fresh session weekly. Open a new conversation with no warm cache and check whether the personality survives. If the first three messages feel like a generic chatbot, the files are too vague or not loading.
  • Keep the files in version control. Your agent's personality is an asset.

What to avoid

  • copying someone else's SOUL.md verbatim (uncanny because it is not yours)
  • performative tough-guy voice ("I'm a no-bullshit operator who tells it like it is" reads as cringe)
  • personality that contradicts the model's actual capabilities
  • letting files drift out of sync with how you actually want the agent to behave today
