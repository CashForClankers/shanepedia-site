Agent Leverage Stack — How Shane Actually Uses AI

This is the actual leverage stack — not a wishlist. Every piece below is wired into Shane's machine right now and earns its place by being used. The goal is to map what is actually getting work done, so the next time someone asks "what's your AI setup", there is a single page to point at, and so future pruning decisions have something concrete to argue against.

Layer 1 — Model routing

OpenClaw exposes a fleet of models as aliases in ~/.openclaw/openclaw.json. The point of routing is to avoid burning frontier-model time on jobs that any decent model can do, and to keep one model in primary so behavior is predictable.

  • codex (openai-codex/gpt-5.4) — daily driver. Primary model for the Best Robot main agent and most cron jobs that need real reasoning. The default for "do this thing well."
  • codex53 (openai-codex/gpt-5.3-codex) — fallback and the model that runs the 2-hour heartbeat. Cheaper, still strong on code and structured tasks.
  • codex-mini (openai-codex/gpt-5.1-codex-mini) — small jobs, summarization, classification. The "don't waste tokens" lane.
  • flash (openrouter/google/gemini-3-flash-preview) — grounded search, public web research, the YouTube spark candidate fetcher. When the answer needs to come from outside the machine, route through Gemini.
  • sonnet (openrouter/anthropic/claude-sonnet-4.6) — long-form prose, writing voice, anything that has to read well at human-paragraph length. Used by the wiki-gen and Shanepedia daily-page paths when they need to write, not just plan.
  • haiku (openrouter/anthropic/claude-haiku-4.5) — cheap, fast formatting, tiny ops, "is this still relevant" classification.
  • qcoder / devstral / codestral / deepseek-code — the code-experiment shelf. Live in routing as comparison candidates for the weekly PinchBench review. Not primary for anything; promotion requires evidence.

The PinchBench Weekly Review (Mondays 8:45) is the actual mechanism that keeps this list honest — see [[operating-rituals.md]]. If a model isn't winning a slot in benchmarks against the incumbent, it stays on the bench.

Layer 2 — The skill library

Skills are the unit of agentic work. They live in ~/.openclaw/skills/ and ~/setup-mac/.agents/skills/, follow the Agent Skills open standard (a directory with SKILL.md containing YAML frontmatter and instructions), and are invoked by name. The currently installed set spans:

  • Vendor surfaces — claude-code, claude-desktop, codex, gemini for native CLIs/UIs of each model vendor.
  • Cloudflare lane — cloudflare, wrangler for deploys, the same lane that backs [[../entities/openclaw.md]].
  • Knowledge/wiki — obsidian, wiki-gen, llm-kb, imp-doc, pdf, summarize for the Shanepedia maintenance loop.
  • Agent ops — openclaw-ops, openclaw-power-ops, openclaw-backup, agent-cli-stack, find-skills, skill-creator for keeping the gateway healthy.
  • Channels and capture — apple-notes, apple-reminders, calendar-reminders, local-whisper, screenshot, youtube-transcript-yt-dlp.
  • Lane-specific — bitcoin-local-map, shanepedia-daily-page, shanepedia-weekly-roundup, random-interesting-thing, meme-factory, memes, shopping.
  • Quality + safety — security, ralph (the looping orchestrator), web-perf, playwright, design-md.

The principle: skills are durable, version-controlled instruction surfaces. New behavior almost never needs a new model — it needs a new skill that routes work through the existing models cleanly.

Layer 3 — Cron-driven schedule

Crons turn the gateway from a chat tool into a system. The push-based surfaces (see [[cron-as-product.md]]) are where most of the daily leverage actually lands. Currently active:

  • Morning Briefing (07:00 daily) — calendar + memory + voice contract, 90 words.
  • Bitcoin + El Salvador Pulse (08:30 Mon/Wed/Fri) — price + one fresh ES signal, 80 words.
  • PinchBench + Stack Review (08:45 Mon) — model routing + software upgrade decisions.
  • Shanepedia Daily Page (11:00 daily) — random wiki page + Gemini YouTube find + ask for updates.
  • Shanepedia Random Spark (12:30 daily) — broader cross-interest spark.
  • Shanepedia One Bet (14:37 Tue/Thu/Sat) — single business bet with proof step.
  • OpenCluck Weekly Hardware Spark (10:00 Wed) — one concrete coop-build action.
  • Shanepedia Weekly Roundup (19:00 Sun) — what changed, what's open.
  • Weekly Reset Brief (20:00 Sun) — kept / dropped / next.

See [[../entities/the-shanepedia-cron-system.md]] for the Shanepedia-specific subset.

Layer 4 — Personality stack

Three files in ~/.openclaw/workspace/ anchor every fresh session:

  • SOUL.md — voice, register, what to never do.
  • IDENTITY.md — who the agent is and what it's loyal to.
  • USER.md — who Shane is, how he thinks, what he's building.

The voice contract for one-shot deliverables (briefings, pulses) lives at ~/.openclaw/workspace/config/daily-update-voice.md and is enforced by being read into every cron prompt. See [[voice-and-style.md]] for the canonical writing rules and [[agent-personality-design.md]] for the design argument behind treating personality as a first-class surface.

Layer 5 — Multi-channel reach

Output isn't useful if it lands in a terminal Shane isn't watching. Channels:

  • Telegram (primary) — bot token in config, allowlist of one user, push-based reach to Shane's phone. Every cron above lands here.
  • ACP — local agent-to-agent protocol surface for tools that talk back to OpenClaw.
  • Discord (configured, currently disabled) — second channel for guild-scoped reach if/when group surfaces matter.
  • Claude Code (web app) — the GitHub/Gmail/Calendar/Drive connectors are wired; that's the surface for tasks that need a real keyboard.

How it composes

The leverage isn't any one piece. It's that a Telegram message at 11am can route through the codex model, hit the shanepedia-daily-page skill, read the SOUL voice contract, query the live wiki, and come back as a 90-word note that knows what Shane was working on yesterday — without Shane having opened anything. That single composition is the product. Everything else is supporting infrastructure for that move and a few dozen variants of it.

If a piece of this stack stops contributing to a move like that, it should be cut. The point of mapping the stack is to make those cuts obvious.
